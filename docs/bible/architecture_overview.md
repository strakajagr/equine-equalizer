## 1. Scope of this bible

Architecture Overview answers two questions: **"what does Equine Equalizer (EE) look like at the runtime-context level?"** and **"how do I find which bible to read for X?"** Audience: any reader who needs the system map (Lambdas, EventBridge rules, ECS Fargate fleet, RDS PostgreSQL, S3, API Gateway v2, ECR, SNS, Secrets Manager) or who needs to navigate to a specific bible for deeper detail.

Architecture Overview is the **bible-corpus-level entry point** and **navigation hub**. § 4.3 below serves the index function for the entire 7-document bible corpus (per BIBLE_STRUCTURE_SPEC v6 § 7.5; the substantive citation is in § 4.3 itself). By design, every other Phase 1 bible's Scope section cross-references back to this document for system topology; this bible cross-references outward for per-domain depth.

**Boundary statements — what Architecture Overview documents:**
- Runtime-context inventory across 8 AWS resource classes (Lambda, ECS Fargate, RDS PostgreSQL, S3, API Gateway v2, EventBridge, ECR, SNS + Secrets Manager).
- Canonical cross-runtime objects (the dataclasses in `backend/models/canonical.py` that cross runtime contexts unchanged in shape).
- INDEX (per § 4.3) — pointers to the 6 specific-domain bibles.
- Operational discipline overrides (per § 3.11) — out-of-band modifications intentionally diverging from CDK-managed-or-Bootstrap-managed default behavior; substrate-as-is-now disposition with CDK reconciliation cycle as future IaC-promotion venue.

**Boundary statements — what Architecture Overview does NOT document:**
- Per-table schema → `database_schema_bible.md` (see § 4.3).
- Per-flow detail (how data moves through pipelines) → `data_pipeline_bible.md`.
- Per-feature provenance (which model uses which feature, what breaks if you change feature X) → `feature_provenance_bible.md`.
- Per-model architecture (ranker layers, calibration, ensembling) → `ml_layer_architecture_bible.md`.
- Per-model success criteria + retrain triggers → `model_evaluation_retraining_bible.md`.
- Per-route detail (HTTP routes, request/response shapes, frontend consumers) → `api_frontend_bible.md`.

Cross-cutting topics that span multiple bibles cite the canonical-home bible per BIBLE_STRUCTURE_SPEC v6 § 5.3. This bible is the canonical home for runtime-topology invariants (e.g., "how many Lambdas exist," "what State are they in," "what target does each EventBridge rule hit"); it is NOT the canonical home for per-component bug histories.

## 2. Definitions

Terminology specific to Architecture Overview's domain. Acronyms defined here once are referenced (not redefined) in other bibles.

- **Runtime context.** A distinct AWS-resource class in EE's runtime architecture: compute (Lambda, ECS Fargate), data (RDS PostgreSQL, S3), connectivity (API Gateway v2), scheduling (EventBridge), config/secrets (Secrets Manager), messaging (SNS), image registry (ECR). § 3.1 through § 3.11 enumerate the resource classes (with § 3.8 holding 2 services: SNS + Secrets Manager; new at v3-patched-b: § 3.9 IAM roles, § 3.10 CloudWatch alarms, § 3.11 Operational discipline overrides). A "canonical" object is one whose shape does not change as it crosses these contexts (per § 4.1).
- **Canonical cross-runtime object.** A Python dataclass at `backend/models/canonical.py` whose shape (field names, types, semantics) is identical when produced by training, consumed by inference, and serialized by the API. Per § 4.1.
- **Active vs Inactive Lambda state.** AWS Lambda function `Configuration.State` enum. `Active` = function is invokable. `Inactive` = function is NOT invokable; AWS will return an error on invoke. At v3-patched-b lock (2026-05-11): 8 of 8 Lambdas Active (per `aws lambda get-function` per-Lambda re-verification 2026-05-11T14:30Z UTC; V16–V22 SP-resume substrate). **[Historical: at v3-patched-a lock 2026-05-08, EE had 3 INACTIVE functions with `StateReason = "The function is trying to use a deleted image."` — meaning the ECR image the Lambda's `Configuration.ImageUri` points to has been culled from the CDK-managed assets repository. Restored at OCRC 2026-05-09 + Phase β-2 cdk deploy 2026-05-11. Per R8 Option B retention discipline (this bible UC), the State-claim example is preserved for pattern instruction value: Lambda State drift is a substantive case study in operational substrate failure modes (per § 3.11 + F1/F7/F10 banking findings).]**
- **ENABLED vs DISABLED EventBridge rule.** Rule scheduling state per `aws events list-rules`. `ENABLED` = cron fires on schedule. `DISABLED` = cron does not fire. EE has 13 rules: 10 ENABLED + 3 DISABLED (per § 3.6 enumeration; substrate-confirmed at SP-A1 V7 + V25). The ENABLED-rule-targeting-INACTIVE-Lambda case produces a fire-and-fail pattern: the cron triggers but invocation fails because the target image is deleted. At v3-patched-b lock: zero ENABLED rules target Inactive Lambdas; fire-and-fail anomaly fully retracted (per V16–V22 SP-resume substrate). Historical reference preserved at § 3.6 anomaly note + § 6.
- **Deployed image.** The ECR image tag the Lambda's `Configuration.ImageUri` points to, as opposed to the source code in the working tree. Pre-baseline-commit (87dec36, 2026-05-04), working-tree code may diverge from deployed images; post-baseline, working tree is the source-of-deployed-code per META_PLAN v9 § 4.5 Tier 4. **At v3-patched-b lock, Phase β-2 cdk deploy 2026-05-11 confirms working-tree-to-deployed-image reproducibility for equine-ingestion (per F14 banking: cdk-asset-pushed image at 2026-05-11T13:58:54Z produced byte-identical digest to OCRC Fix 6 v2 image at 2026-05-09T17:16:13Z; source-side fix per OCRC close-out § 3.1 durable across CDK reconciliation cycles).**
- **WR / PL / LS.** The three inference pipelines: WR (`win-and-rank`, family `wr` for both training and inference), PL (`place-and-show` / `place_show`, family `pl`), LS (`longshot`, family `ls`). Each has a daily inference Lambda (`equine-wr-inference`, `equine-pl-inference`, `equine-ls-inference`), a per-model artifact path `s3://equine-model-artifacts/<family>/<version>.json`, and a per-pipeline prediction shape (per § 4.2 — three independently-defined dataclasses, no inheritance).
- **Gonzo Sauce.** Operator-stated terminology for a feature subset added in Phase A3. Defined here once for cross-bible reference; canonical home for substantive feature documentation is `feature_provenance_bible.md`.

When sources conflict, source-priority hierarchy applies per META_PLAN v9 § 4.5: Tier 1 (live AWS state) > Tier 2 (live API endpoints) > Tier 3 (live database state) > Tier 4 (working-tree code post-baseline 87dec36) > Tier 5 (operator-stated history) > Tier 6 (`EE_CURRENT_STATE_DUMP.md` baseline) > Tier 7 (session logs).

### 3.13 L1 idiom-deviation + substrate-preservation rationale (BP-A5.4 v3-patched-f NEW subsection per Phase A E4 Step 3 Path A operational substrate)

This subsection documents two L2-idiom deviations applied in `infrastructure/cdk/lib/compute-stack.ts` per Phase A E4 Step 3 Phase 2 Path A reconciliation closure. Both deviations are substrate-preservation moves: each preserves operationally-correct AWS-existing state via CDK property override patterns, rather than letting CDK auto-managed L2 idiom generate divergent state.

#### 3.13.1 L1 `iam.CfnRolePolicy` deviation for 5 AsyncDLQSend resources (Phase 1.5 substrate)

**Idiom-deviation scope**: 5 AsyncDLQSend IAM inline policies attached to 5 Lambda execution roles (Ingestion / Results / WRInference / PLInference / LSInference).

**L2 idiom** (pre-deviation default): `role.attachInlinePolicy(new iam.Policy(this, 'AsyncDLQSend', { ... }))`. CDK synthesizes this as `AWS::IAM::Policy` CFN resource with `Roles: [<role-name>]` property.

**Deviation rationale**: AWS CloudFormation IMPORT change-sets require importable resources to have unique-identifier ResourceIdentifier schemas (per `aws cloudformation describe-type --type RESOURCE --type-name <type>`). The `AWS::IAM::Policy` resource type requires standalone managed-policy ARNs for import (primary identifier path). Inline policies attached to existing CLI-deployed Lambda roles do NOT have standalone policy ARNs — they are sub-statements within the role's inline-policy collection. **L2 `iam.Policy` synthesis is therefore IMPORT-incompatible** for this substrate state.

**L1 deviation pattern applied at Phase 1.5**: `new iam.CfnRolePolicy(this, 'X', { policyName: 'AsyncDLQSend', roleName: fn.role!.roleName, policyDocument: {...} })`. Synthesizes as `AWS::IAM::RolePolicy` CFN resource type with `primaryIdentifier: ['/properties/PolicyName', '/properties/RoleName']` — IMPORT-compatible per AWS schema substrate (verified via `aws cloudformation describe-type --type RESOURCE --type-name AWS::IAM::RolePolicy`).

**Loop pattern preserved**: the `for (const { fn, id } of dlqAttachedLambdas) { ... }` loop preserves the prior 5-Lambda iteration pattern with L1 substitution inside the loop body. No iteration semantic change beyond construct-level idiom shift.

**Operational verification**: A4.1 IMPORT change-set executed with `e4-resources-to-import.json` listing all 5 AsyncDLQSend resources with `ResourceType: AWS::IAM::RolePolicy`; all 5 imported cleanly to CFN management with status UPDATE_COMPLETE.

**Forward implication**: any future CDK developer working on the AsyncDLQSend constructs should understand that L1 `iam.CfnRolePolicy` is intentional, not legacy artifact. Reverting to L2 `iam.Policy` would break the import-compatibility contract.

#### 3.13.2 A4.2.5 target Id substrate-preservation (`etp-daily` preserved over CDK auto-generated `Target0`)

**Idiom-deviation scope**: 1 EventBridge Rule target Id field (`EntriesTracksPublisherSchedule183F4E6D.Properties.Targets[0].Id`).
